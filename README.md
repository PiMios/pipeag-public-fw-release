# PipeAg scale sensor — public firmware releases

Firmware images for the PiMios PipeAg BLE scale sensor (Silicon Labs
BGM210PB32JIA). Published here so the PipeAg flash tool — and anyone updating a
unit with EFR Connect / Simplicity Connect — can download them without a GitHub
account.

**Everything under [Releases](../../releases) is what you want.** Each release
carries the firmware images, the customer indicator-configuration sheet, and a
`manifest.json` describing every asset.

## This repository is a one-way mirror. Do not commit here.

| | |
|---|---|
| **Source of truth** | a private PiMios repository, maintained by PiMios |
| **This mirror** | written only by automation, on `release: published` upstream |
| **Direction** | source → here, one way, never back |
| **Covers** | release assets and the generated `manifest.json` / `index.json` |

Nothing is ever hand-pushed here and nothing is ever pulled from here back into
a source repository. That is deliberate rather than lazy: this repository ships
**per-indicator firmware images**, and each image is only correct for the one
indicator profile it was compiled for. Two writable copies of firmware is
precisely how an image ends up distributed against the wrong profile — and a
mismatched image does not fail loudly, it reports **silently wrong weights**.
One writer, one history.

Found a problem? Raise it with your PiMios contact. A pull request opened here
cannot be merged into the firmware.

## Read this before you flash anything

**The filename is not sufficient to identify an image.** Use `manifest.json`.

Every release is gated before it is published. For each image, the publish job
reads the version out of the container's own bytes (the patched GATT Firmware
Revision String, `0x2A26`), reads the flash address range out of the S-record
addresses or the GBL tag stream, recomputes the GBL `END` CRC32, and refuses to
publish if any of it disagrees with what the filename or the release claims. So
the numbers in `manifest.json` came from the images, not from their names.

One thing is **not** in the bytes, and no amount of checking can put it there:

> `SCALE_MODEL` — the indicator profile — is a compile-time define with **no
> runtime marker**. One image is one indicator profile, and nothing in an
> image's bytes says which.

The `scale_model` in `manifest.json` is therefore a *statement made by the
release process*, carried alongside the image. Where it says `null`, nobody
stated a profile: treat that as unknown and confirm before flashing. Never
infer a profile from the `_tN` in a filename — that is a naming convention, not
evidence.

### Specific cautions

- **`frm23_t5.gbl` (1.0.23, profile 5) is for the Rice Lake 720i only.** It
  restores a trailing zero that indicator omits. On any other indicator it
  **over-reports by 10×**.
- **Profile 6 (1.0.24) under-reports by 10× on a Rice Lake 720i**, for the same
  reason in reverse. Use profile 5 there.
- **OTA takes the application-only `.gbl`.** The `.s37` is for SWD / factory
  programming.
- **Never flash a `.bin`.** A raw binary carries no load addresses at all.
- A unit's installed version is whatever it reports on GATT `0x2A26`. That is
  the only reliable statement of what is on a device.

## Files

| File | What it is |
|---|---|
| `manifest.json` (per release) | Every asset with its size, sha256, the version read out of its bytes, the address ranges it programs, and its stated indicator profile |
| `index.json` (this branch) | The same, across every published release — one unauthenticated fetch, no API rate limit |
| `frmNN_tM.gbl` | BLE OTA image, application only |
| `frmNN_tM.s37` | SWD / factory programming image |
| `bootloader-second-stage.s37` | Gecko Bootloader; flash **before** the application on a blank module |
| `firmware_indicator_config_lookup.xlsx` | Customer-facing sheet mapping indicator serial settings to the image to flash |

Verify what you downloaded against the `sha256` in `manifest.json` before
flashing it.
